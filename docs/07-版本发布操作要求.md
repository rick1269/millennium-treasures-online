# Codex 版本发布操作要求

本规范适用于 Codex 对本仓库的每次提交。`main` 是 GitHub Pages 的线上发布分支，推送到 `main` 就可能更新玩家看到的网页；因此提交、部署和验证必须作为同一次发布处理。完整源码标签从 `source-baseline-v2.3.1` 开始有效；更早的标签只包含网页构建物。

## 0. 发布前门禁

1. 确认目标提交包含 `web/`、`supabase/functions/`、`supabase/migrations/`、`package.json`、`package-lock.json` 以及需要的根目录网页构建物。检查 `git status`、目标分支和 `git diff`，不得提交密钥、`cloud-public.json`、本地房间数据或临时配置。
2. 按 `AGENTS.md` 运行所需的产品文档生成与检查；运行 `npm ci`、`npm test`、`npm run build:cloud`。确认 GitHub Pages 根目录文件与 `cloud-site/` 的构建结果一致。仅文档修改也要执行对应文档检查。
3. 用 Supabase CLI 查看本地与远端迁移编号，并核对真实数据库结构。若历史与结构不一致，先查明原因并修复；不得直接 `db push`，也不得只凭文件名把迁移标为已应用。
4. 先在本地创建待发布提交，记录完整 SHA。提交之后若修改任何发布输入，必须重新提交并重新检查。不得先推送到 `main` 来取得 SHA。

## 1. 数据库迁移

从待发布提交读取迁移文件，按编号顺序应用尚未执行的迁移。已有迁移只读；新变更创建新的时间戳 SQL 文件。应用前检查 SQL 对现有房间和旧版云函数的兼容性，必要时先做数据库备份。执行后再次查看 Supabase 迁移列表，确认远端编号与本次目标一致，并记录完整编号。不能用 `git switch` 撤销已执行的 SQL。

**历史记录初始对齐：** 2026-09-26 已核对线上表、列、索引、约束、RLS 与权限，确认 `202609240001`、`202609240002`、`202609240003` 的 SQL 变更已存在，并将三条编号标记为已应用；随后通过 `supabase migration list` 复查本地与远端一致。后续发布每次仍须重新查询，发现偏差时按真实数据库状态处理。Supabase 的迁移历史与 Git 文件是两套记录，必须保持一致。具体方法见 [Supabase 官方迁移文档](https://supabase.com/docs/guides/deployment/database-migrations)。

## 2. 云函数

从**同一个提交**同步规则引擎并部署 `game` Edge Function，例如执行项目已有的 `npm run deploy:game`。验证函数部署成功，检查其版本或部署时间，并用实际房间请求确认 API 能读取当前数据库结构。失败时停止，不发布网页。

## 3. 网页

确认仓库根目录的 GitHub Pages 构建物与待发布提交一致，再推送该提交到 `main`。等待 GitHub Pages 发布完成，打开线上首页与手册，确认静态资源能加载、网页实际版本对应目标 SHA，并完成一次基本房间操作。不要通过直接编辑线上网页绕过 Git。

## 4. 发布验证与版本记录

验证数据库、云函数和网页均为目标版本后，创建附注标签并推送。每次发布使用唯一标签；标签必须**指向刚才发布的提交**，不能复用旧标签。标签说明至少包含以下字段：

```text
Commit: <完整 40 位 SHA>
Migrations: <远端已应用迁移编号，按升序列出；无新增也记录当前编号>
Edge Function: game <部署时间或版本标识>，<验证结果>
Web: <Pages 发布运行链接或时间>，<线上页面验证结果>
Checks: <测试、构建和实际房间验证结果>
```

发布结果向用户报告标签、SHA、已应用迁移编号、网页地址、云函数状态和验证结果。若部署中断，报告**已完成到哪一步**；修复后从失败步骤继续，并重新验证整个组合，不能创建“已发布”标签。

## 回退

网页和云函数可以从同一个旧标签重新部署，但先确认旧函数兼容当前数据库。数据库结构或数据变化须用新的修正迁移或经过验证的备份恢复。回退完成后照样执行线上验证并记录新的发布标签；不得移动或重用既有标签。
