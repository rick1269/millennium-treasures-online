# 千年藏珍：云端账号与联机部署

## 当前架构

- **GitHub Pages** 公开提供静态网页。网页只包含 HTML、CSS、浏览器 JavaScript 和 Supabase 的 publishable key。
- **Supabase Auth** 负责邮箱注册、验证、登录与刷新会话。
- **Supabase Edge Function `game`** 校验账号令牌或游客席位凭证，调用原有规则引擎推进回合与机器人，并返回按玩家身份裁剪的局面。
- **Supabase Postgres** 保存房间状态；房间表开启 RLS 且不授予 `anon` / `authenticated` 直接读写权限。玩家只能通过 Edge Function 操作。
- **连接记录表 `game_presence`** 保存真人席位的最近连接时间与页面实例 ID。服务端据此启动机器人托管，并防止旧页面迟到的关闭通知覆盖新连接。

浏览器关闭或电脑关机后，已部署的游戏服务仍由上述云服务运行。公开房间码允许旁观；操作需要账号身份或当前浏览器会话内的游客凭证，并占有该房间的真人席位。

## 玩家使用

1. 打开网页，选择“以游客身份进入”，或填邮箱和密码注册并验证邮箱后登录。
2. 输入称呼创建房间；把带房间码的链接发给朋友。
3. 朋友可选游客或账号身份加入。房主也可以设 2–5 位机器人，独自开始。
4. 公开旁观者只能看公开局面，不能查看私牌、密封报价或替玩家操作。

登录会话保存在当前浏览器，过期后自动刷新。游客凭证只存在当前浏览器会话的 `sessionStorage` 中；刷新页面可继续，关闭浏览器后无法找回原席位。网页关闭通知会在约 8 秒后触发托管；通知未送达时，连接心跳超时约 1 分钟后触发。其他在线玩家的下一次房间刷新会执行托管；若全员离线，下次打开房间时才推进游戏。账号玩家重开房间即可停止托管、接管原席位。游客托管后服务端删除原席位的凭证摘要，不能重新接管。托管保留原席位的牌、金币和房间内结算。游客不生成账号历史战绩；平台排行榜目前尚未提供，未来实现时应排除 `isGuest` 席位。公共电脑使用账号后请点击“退出”。

## 项目文件

| 文件 | 用途 |
| --- | --- |
| `supabase/migrations/202609240001_game_rooms.sql` | 数据表、索引、RLS 和权限 |
| `supabase/migrations/202609240002_guest_rooms.sql` | 允许无账号房主创建游客房间 |
| `supabase/migrations/202609240003_player_presence.sql` | 记录连接心跳与网页关闭通知 |
| `supabase/functions/game/` | 服务端 API |
| `supabase/functions/_shared/` | 同步后的规则引擎与卡牌目录 |
| `scripts/sync-cloud-game.js` | 把 `web/game.js` 与 `web/catalog.js` 同步到 Edge Function |
| `scripts/build-cloud-site.js` | 生成静态网页目录 `cloud-site/` |
| `cloud-public.json` | 仅含公开的项目 URL 与 publishable key；本地保留 |
| `web/` | 本地版与云端版共用的页面和规则源码 |

改动规则源码后先运行 `node scripts/sync-cloud-game.js`，再部署函数。改动页面后运行 `node scripts/build-cloud-site.js`，再上传 `cloud-site/` 中的所有文件和素材目录。

## 从零部署

1. 在 Supabase 免费项目的 SQL Editor 按编号顺序执行三个迁移文件。已有项目需执行 `202609240002_guest_rooms.sql` 和 `202609240003_player_presence.sql`。
2. 在 Authentication → URL Configuration 把 Site URL 和允许的 Redirect URL 设成网页地址；保留 **Confirm email** 开启。
   在 Authentication → Emails → SMTP Settings 选择自定义 SMTP。个人 163 邮箱填写 `smtp.163.com`、端口 `465`、完整邮箱地址作为发件地址和用户名；密码使用网易邮箱的 **SMTP 客户端授权码**，不要使用邮箱登录密码。授权码仅在 Supabase 控制台填写，不写入代码、文档或 GitHub 仓库。保存后用一个非组织成员邮箱实际注册，确认能收到验证信。
3. 安装项目依赖：`npm install`。
4. 设置 `SUPABASE_HOME` 为当前文件夹内目录，再用 Supabase CLI 登录、部署函数；函数须关闭平台网关的 `verify_jwt`，代码内会分别校验玩家令牌。项目的 `supabase/config.toml` 已声明此配置。
5. 填写 `cloud-public.json`（可复制 `cloud-public.example.json`）；只能填 **publishable** key，不能填 `sb_secret_`、service_role、数据库密码。
6. 构建网页并把 `cloud-site/` 的静态文件同步到仓库根目录，供 GitHub Pages 发布。同一提交还要保存 `web/`、`supabase/functions/`、`supabase/migrations/`、`scripts/`、`tests/` 与依赖锁文件，再打完整源码标签。`cloud-public.json`、游戏存档、原始分层插画、配置目录和服务器密钥不得提交。
7. 用不同浏览器会话验证账号与游客建房、入席、刷新页面、机器人、拍卖、关闭网页后的托管、游客无法重新控制原席位，以及账号玩家重新登录后接管。

### 163 邮箱返回 535 时

Supabase Auth 日志若显示 `POST /signup`、HTTP 500、`535 authentication failed`，说明请求已到达邮件服务器，但 SMTP 登录被拒绝。先确认 **Supabase 的 Sender email address、Username 和生成客户端授权码时登录的 163 邮箱是同一个账号**；检查 SMTP 服务已开启，密码栏填的是最新客户端授权码，没有多余空格。保存后再注册一次，并查看同一时间的 Auth 日志。

若仍失败，在本机终端运行 `python3 scripts/check_163_smtp.py`。脚本会隐藏输入授权码，只尝试登录 `smtp.163.com:465`，不发送邮件，也不保存邮箱或授权码。若本机也得到 535，应从 163 账号设置和授权码入手；若本机登录成功而 Supabase 仍得到 535，应重新在 Supabase 保存同一授权码并检查其 Auth 日志。不要把授权码写入聊天、命令参数或项目文件。

## 免费版配额与隐私

Supabase 内置邮件服务**只向项目组织成员发信**，且本项目控制台显示每小时最多 **2 封**。因此，若要让外部朋友使用“邮箱验证后登录”，必须先配置自己的 SMTP 服务。未配置前，网页虽然能打开注册表单，外部邮箱仍无法收到验证信。Edge Function 与数据库也受免费额度约束；网页保持打开时每 4 秒发送一次房间心跳。参见 [Supabase 官方 SMTP 说明](https://supabase.com/docs/guides/auth/auth-smtp)。

免费项目长时间无人使用时可能被 Supabase 暂停，需要在控制台恢复；详情见 [Supabase 上线检查表](https://supabase.com/docs/guides/deployment/going-into-prod)。

房间码是公开旁观入口，不等于私密邀请码。不要把房间码当作保密信息。账号玩家由 Supabase Auth 用户 ID 绑定，游客玩家由 48 位随机凭证的 SHA-256 摘要绑定。游客凭证不进入 URL，服务端只将摘要写进房间状态；每次操作都验证对应席位。数据库内的房间状态可能包含私牌与报价，因此前端 publishable key 没有直接访问该表的权限。
